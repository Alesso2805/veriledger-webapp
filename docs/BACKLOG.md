# VeriLedger webapp — backlog and sprint plan

Oct 20, 2026 · @Alessandro David

46 stories in 7 epics (E0 to E6). E0 records what was built on July 29, 2026, retroactively, so that the audit can check each criterion against a test; VLW-07 is the documentation of October 20. E1 to E4 come from the audit of the same day ([AUDIT.md](AUDIT.md)). E5 (VLW-27 to VLW-34) builds design direction E, chosen the same day ([ADR-0004](adr/0004-design-direction-e.md), [DESIGN.md](DESIGN.md)), and absorbs VLW-20; VLW-34 follows the API's ADR-0006 (visitors browse without an account and start a demo with one click). VLW-35 and VLW-36 come from the audit of October 21 that looked for anything able to blank the app (#53, #54). E6 (VLW-37 to VLW-48) moves the webapp to design direction C, in English and Spanish and in light and dark themes, chosen by the product owner on October 22 after seeing C, D and E drawn in full ([ADR-0006](adr/0006-design-direction-c.md), [ADR-0007](adr/0007-two-languages.md), [ADR-0008](adr/0008-light-and-dark-themes.md)). MoSCoW priority (M = Must, S = Should, C = Could) and estimate in points (1, 2, 3, 5, 8). IDs VLW-08, VLW-09 are left free.

**Redesign early, in order** (product owner, 2026-10-20). The redesign does not wait for the rest of the plan, and it does not run ahead of the API either:

- Sprint 1 builds design E's foundation (tokens, shell, login, states) on a repository that compiles, with tests and CI.
- Each view lands in the sprint where its data exists. The API brings its data endpoints forward to its Sprint 2.
- Deployment stays in Sprint 4.
- Pages that are about to be replaced are not cleaned up; their replacements follow the comment rules from the start.

The API's stories (VLA-NN) live in `veriledger-api/docs/BACKLOG.md`. Both backlogs use the same sprint numbers and dates; a story that needs its counterpart says so and merges after it.

**Order inside Sprint 1.** VLW-11 first (nothing else is green without it), then VLW-12, VLW-10, VLW-13, VLW-27, VLW-33, and VLW-14 last on the files that survive.

**Order inside Sprint 2.** VLW-15 and VLW-16 first (the signing library and local keys), then VLW-30 on top of them, VLW-18 once the API's nonce exists, VLW-17, and VLW-28 when VLA-20 and VLA-33 are merged.

**Order inside Sprint 3** (product owner, 2026-10-21). First the views whose data is on the API's main: VLW-29 (VLA-20), then VLW-31 (VLA-34). Next, VLW-19, whose generated types need the API's `docs/openapi.json`. Then VLW-34, when VLA-35 is merged (VLA-36 already is), and VLW-32 when VLA-19 is merged.

**Order inside Sprint 4** (product owner, 2026-10-21):

1. VLW-24 first, since it depends on nothing.
2. VLW-23 once VLA-21 (`CORS_ORIGINS`) and VLA-24 (seeded users from the environment) are merged. It runs against the API's published image (VLA-22) and its Compose (VLA-23), both already merged.
3. VLW-25 with VLA-27.
4. VLW-26 last, because its screenshots come from the deployed instance.
5. VLW-35, then VLW-36, added by the product owner on 2026-10-21 while the deployment waits for its server. The fuzzer checks that the fallback never shows, so the fallback comes first.

**Order inside Sprints 5 and 6** (product owner, 2026-10-22):

1. VLW-37, the decisions.
2. VLW-38, the canvas: nothing is built in C before its dark theme and its Spanish texts are drawn.
3. VLW-39, then VLW-40: the tokens and themes, then both languages on the pages as they are. Each later story then changes only a page's look.
4. VLW-41 and VLW-42, the shell and the sign-in, closing Sprint 5.
5. VLW-43 to VLW-47, one view each, in Sprint 6.
6. VLW-48, then VLW-26: release 1.0.0 with screenshots of C, taken from the deployed instance.

Until then the server keeps its pinned image, so visitors never see a half-redesigned app.

**Buffer.** Sprints 2 and 3 carry 17 points each. If a sprint does not close, move out the "Should" stories (VLW-14, VLW-19, VLW-24, VLW-26, VLW-32) before cutting quality on a "Must". A view whose API data is late waits; it is never built on invented data (DESIGN.md).

**Design.** A view is done when it matches its artboard in the canvas (DESIGN.md) at 1280 and 360 px, with the same tokens and the same animations. From epic E6: at 1440, 768 and 360 px, in both themes and both languages. A difference is fixed in the code or, if the design was wrong, in the artboard and DESIGN.md in the same PR.

**Minimum ceremonies.** Shared with the API: 30-minute planning, a 5-minute demo at the close, and a 3-line retrospective in each repository's `docs/sprints/sprint-N.md`.
